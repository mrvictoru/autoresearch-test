Ratcheting Harness
PyCon HK 2026 · Overview
A 15-minute pattern for LLM-driven iteration

Build your own ratcheting experiment harness in Python.

A strict, reproducible loop that turns "chat with an LLM" into a score-driven search. One mutable file. One fixed simulator. One ledger.

What you will leave with

1.One sentence that explains the entire pattern.
2.Four safety checks that prevent silent cheating and noisy scores.
3.One 30-line skeleton you can copy into a new repo tonight.
4.One live example — a real restaurant inventory benchmark — to ground all of it.
Mental model: "We let the LLM edit one file, score it, and only keep strict improvements. Everything else is plumbing."

Why a new pattern at all?

  • Vibe coding — paste, eyeball, ship. Fine once, broken at iteration 200.
  • Unconstrained agents — write anywhere, edit the tests, drift the score.
  • Ratcheting harness — one file, one simulator, one ledger, strict better-than-best.

Same idea works for scheduling, bidding, prompt selection, and any other scalar-scored problem.

  • Simulator — frozen. Function from policy → score. Trusted.

Slide 3 · The loop
Seven steps, one column

The loop, end to end.

Walk top-to-bottom. Everything else in this talk is a defense of one of these steps.

Lifecycle of one attempt

1

Read the best

Open results.tsv, parse the highest keep row. That is your bar.

2

Edit the policy

Change only train.py (or your domain equivalent). One commit, one file.

3

Pre-check

Run unittest so syntax / import / contract errors fail fast.

4

Evaluate in a fresh process

subprocess + Docker. No shared sys.modules, no leaked globals, no warmed caches.

5

Parse the score

Read score from the --- RESULTS --- block. Never from chat.

6

Decide

Strictly better than the bar? Keep. Else revert via git reset --hard HEAD~1. Crash? Revert and record crash.

7

Append to the ledger

One row per attempt — always, even for discard and crash.

One atomic helper packages it

# scripts/run_once.sh — commit, evaluate, keep/discard, log
./scripts/run_once.sh "tweak safety factor to 1.4"

# Prefer Docker so the Python process is fresh:
docker compose run --rm autoresearch \
  python -m autoresearch.experiments.restaurant_eval \
  --experiment autoresearch/experiments/restaurant_train.py

The shell script and the Docker command are the only two entry points you need to remember. The harness does the rest.

That is the whole loop. The next three slides defend three of those steps.

Slide 5 · Contract
Six lines, the whole API

The duck-typed policy contract.

Runtime-enforced. No base class. The harness looks up the function and the method by name and refuses to run if either is missing.

The minimum viable policy

# train.py — the LLM's only writable surface
def build_policy():
    return MyPolicy(...)


class MyPolicy:
    def fit(self, scenarios, task): ...         # optional
    def decide_orders(self, observation): ...   # required
  • Runtime-enforced — getattr + hasattr. No Protocol needed.
  • Stable across domains — restaurant, scheduling, bidding, routing: same shape.
  • Only thing the LLM may change. No imports of internal helpers, no monkey-patching.

How the harness checks it

# autoresearch/experiments/restaurant_eval.py
build_fn = getattr(module, "build_policy", None)
if build_fn is None:
    raise RuntimeError("must define build_policy()")
policy = build_fn()
if not hasattr(policy, "decide_orders"):
    raise RuntimeError("must return an object with decide_orders")

That is the entire interface surface between the immutable harness and the LLM's edits. It is small on purpose.

Slide 6 · Ratchet
Commit, evaluate, decide, append

The ratchet and the ledger.

The whole search is just this loop: read best, run candidate, compare, keep or revert, log.

Six lines that move the frontier

# autoresearch/frontier.py
commit_before_run("candidate: tweak safety factor")
score = parse_score_from_log()
if score > read_best_result("results.tsv")["score"]:
    append_result(..., decision="keep",    message=msg)
else:
    revert_last_commit()
    append_result(..., decision="discard", message=msg)
  • Ledger is the source of truth for "what is the current best."
  • Git is the source of truth for "what code produced this score."
  • Together they are auditable — file → score → commit, on demand.

Slide 7 · The example
One instance of the pattern, not the pattern itself

The restaurant example.

A concrete benchmark that lets us see the ratchet work in public. The point is not the restaurant — the point is the loop around it.

What is the simulator?

  • Horizon — 14 days, two service periods per day (lunch, dinner).
  • State — menu items share ingredients. Each ingredient has a shelf life, a supplier lead time, a per-ingredient storage cap, and a unit cost.
  • Constraints — a global 1000-unit warehouse cap shared across all ingredients.
  • Objective — score = revenue − waste − holding − order − stockout_penalty. Higher is better.

What is the policy file?

  • Path — autoresearch/experiments/restaurant_train.py.
  • Contract — exposes build_policy(). Same contract as slide 5.
  • Current best — a focused residual hybrid: a safe rule-based heuristic plus a small MLP residual on cheese / onion / lettuce / pasta.

If you remember nothing else about the restaurant: the policy is small, the loop is the value, and the simulator never changes.

Build your own ratcheting harness.

Five required files. Four required safety checks. A 30-line skeleton. A porting checklist. The full recipe lives at docs/build_your_own.md.

The minimum viable recipe

  • Five files — task.py, eval.py, train.py (mutable), frontier.py, run_once.sh, plus results.tsv.
  • Four safety checks — fixed seeds, single-file mutation, fresh process, strict better-than-best.
  • Five-step porting checklist:
    1. Define state / action / constraints.
    2. Write a deterministic scenario generator.
    3. Pick a scalar objective.
    4. Build a baseline policy.
    5. Run the ratchet.

→ Open the full recipe

Common pitfalls

  • Forgetting the subprocess boundary — old globals leak into new runs.
  • Letting sys.modules cache leak — always load candidates by path.
  • Accepting the first improvement instead of strict — silent regression.
  • Conflating "score went up" with "model improved" — only strict greater-than counts.

One-sentence takeaway

The LLM is not the trick. The boundary is. Define it, enforce it, and the loop does the work.
